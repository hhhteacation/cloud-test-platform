## 2. 项目当前总体状态

项目已经不再只是前端 Mock 页面，当前已形成以下真实链路：

```text
React + TypeScript + Vite + Ant Design
        ↓
Fastify + TypeScript API
        ↓
SQLite + 本地制品/证据存储
        ↓
按设备隔离的执行队列
        ↓
ADB
        ↓
Android 真机
        ↓
Morpho APK / 平台载体 APK
        ↓
output.mp4、日志、截图、检查结果和报告
```

已经具备的主要能力：

- APK、视频上传与基础校验；
- AAPT APK 元数据识别；
- 平台载体 APK 与 Morpho APK 的协议适配；
- Android 真机发现、注册和状态识别；
- 同一设备串行、不同设备并行的任务队列；
- vivo、HONOR、OPPO/ColorOS 安装确认和权限弹窗的严格自动化；
- 取消任务、失败隔离、运行进度聚合；
- 按设备输出视频、日志、截图和报告；
- HTTP Range 视频播放；
- 安全删除任务和 SQLite 在线备份。

## 4. 已处理的前端与本地开发问题

### 4.1 本地页面无法访问或修改后看不到效果

**现象**

- 用户认为项目没有部署到本地；
- 修改代码后浏览器看不到变化；
- 编辑过程中服务不可访问；
- 旧终端输出与当前服务状态混在一起，难以判断真实错误。

**根因**

- Vite 开发服务没有运行或已经停止；
- 混淆了“开发服务器”和“静态部署”；
- 没有明确理解浏览器、Vite、React、API 之间的调用链；
- 修改源码不等于服务已经重启或产物已经重新构建。

**处理**

- 明确了浏览器 → Vite → React → Fastify API 的本地链路；
- 重新启动开发服务；
- 增加统一脚本和运行说明；
- 区分前端 Mock 模式和真实 API 模式。

**状态：已解决并验证。** 当前前端与 API 均可构建。

### 4.2 `pnpm: command not found`

**真实错误**

```text
zsh: command not found: pnpm
```

初期环境中 Node、npm、corepack 的命令路径也不稳定。

**根因**

- shell 启动文件中的 PATH 配置不完整；
- Homebrew 初始化命令在 Homebrew 不存在或路径不正确时仍被执行；
- pnpm 的命令入口没有稳定加入交互 shell 和登录 shell。

**处理**

- 恢复 pnpm 命令入口；
- 同时更新 `~/.zprofile` 和 `~/.zshrc`；
- 仅在 Homebrew 确实存在时执行初始化；
- 重装/恢复依赖并重新构建。

恢复过程中，离线安装因为本机 pnpm 缓存缺少 Ant Design 依赖而失败，随后使用正常联网安装恢复 `node_modules`。

**状态：已解决并验证。** `pnpm test`、`pnpm build` 均成功。

### 4.3 JSX 语法错误导致前端构建失败

**历史错误**

```text
ExecutionPage.tsx:
JSX attributes must only be assigned a non-empty expression
```

**处理与验证**

当前源码中该语法错误已不存在，重新执行完整构建通过。

**状态：已解决并验证。**

### 4.4 “开始测试”按钮看起来无法点击

**现象**

按钮实际上已经响应并开始上传 APK，但上传后后端拒绝了 Morpho APK；错误提示停留时间短，用户感知为“点击无反应”。

**根因**

旧实现把 APK 包名硬编码为：

```text
com.sdktest.platform
```

真实 Morpho APK 包名为：

```text
com.morphoinc.videopostprocessor
```

同时，表单基础校验过早地与真实设备在线状态耦合，使按钮状态和失败原因更难理解。

**处理**

- 保留 AAPT APK 元数据检查；
- 将单一包名假设改为按 APK 协议识别；
- 对未知 APK 明确拒绝，而不是套用错误协议；
- 错误提示改为更清楚、更持久；
- 文件/表单校验与设备连通性判断分离；
- 离线真机默认禁选，但不再把设备在线状态混成文件格式错误。

**状态：已解决并验证。** 创建任务模型和协议识别已有测试覆盖。

### 4.5 旧版后端缺少 `capabilities` 导致任务列表白屏

**根因**

前端默认认为后端任务对象一定含有 `capabilities`，旧数据或旧接口缺失该字段时，渲染路径发生异常。

**处理**

在 HTTP Client 层进行数据标准化，为旧版响应补齐任务能力信息。

**验证**

自动化测试明确覆盖：

```text
旧版后端缺少 capabilities 时补齐任务能力，避免任务列表渲染白屏
```

**状态：已解决并验证。**

### 4.6 上传校验不完整

**历史问题**

- 空文件可能进入上传流程；
- APK/MP4 后缀不正确时反馈不明确；
- 超限文件、制品缺失的错误不够稳定；
- 前后端校验口径可能不一致。

**处理**

前端和后端均增加了：

- 空文件校验；
- APK、MP4 扩展名校验；
- 配置上限校验；
- 缺失制品检查；
- 明确失败代码和用户反馈。

**状态：部分解决。** 业务层校验已完成，但请求级 multipart 限制仍然过宽，见 P0 风险。

## 5. APK 协议与 Morpho 执行链路问题

### 5.1 Worker 把所有 APK 都当作平台载体 APK

**旧实现硬编码内容**

```text
package: com.sdktest.platform
extras: task_id, auto_run
result.json
output.mp4
/files/tasks/{taskId}/...
```

Morpho APK 的包名、启动方式、输入目录、日志标记和输出命名均与平台载体不同。

**风险**

即使 APK 能成功安装，也可能以错误 Intent、错误路径和错误完成条件运行，最终产生误判或异常输出。

**处理**

新增 `apps/api/src/apk-protocols.ts`，分别识别：

- 平台载体 APK 协议；
- Morpho APK 协议。

每种协议独立定义：

- 输入目录；
- 输出定位；
- 启动命令；
- 进度与完成标记；
- 取消行为；
- 文件名清理规则。

未知 APK 不再被“猜测执行”，而是明确返回 `APK_PROTOCOL_NOT_FOUND` 或 `UNSUPPORTED_APK_PROTOCOL`。

**状态：已解决并验证。** 有协议识别、路径、日志映射和文件名清理测试。

### 5.2 平台传给 Morpho 的输入目录错误

**错误路径**

```text
.../files/tasks/{taskId}/input
```

**官方脚本成功使用的路径**

```text
.../files/VideoStabilizerDataPack
```

**影响**

Morpho 无法按官方 Demo 的预期发现素材，导致输出不一致或失败；早期 vivo 设备曾出现约 8 MB 的可疑输出。

**根因结论**

早期曾怀疑 vivo 设备或算法本身不兼容，但后续对照官方 `batch_process.sh` 后确认，主要根因是 **平台 Worker 与真实 Morpho Demo 协议不匹配**，而不是 vivo 算法兼容性问题。

**处理**

平台输入目录、启动行为、日志和输出读取均对齐真实 Morpho Demo 协议。

**验证**

修复后同类输出约 33.7 MB，且后续设备运行通过。

**状态：已解决并由真实设备记录验证。**

### 5.3 进度和完成条件不适配 Morpho

**历史问题**

旧 Worker 只认识平台载体 APK 的结果文件与进度模型，无法可靠判断 Morpho 是否已经开始、找到输入、处理完成或失败。

**处理**

通过 Morpho 日志标记和文件状态组合判断：

- 批处理开始；
- 已发现输入；
- 正在处理；
- 输出路径；
- 输出文件稳定；
- 明确失败信息。

**状态：已解决并验证。**

### 5.4 平台载体 APK 缺少真实 SDK 实现

仓库当前没有真正的：

```text
com.sdktest.integration.VendorSdkBridgeImpl
```

因此平台载体 APK 走真实 SDK 路径时会返回：

```text
SDK_INITIALIZE_FAILED
```

当前实现没有用“直接复制输入视频为输出视频”的方式伪造成功，这是正确的质量和诚信保护。

**状态：未解决产品阻塞项。** 必须由真实 SDK 集成方提供 `VendorSdkBridgeImpl`，才能完成平台载体 APK 的真实 SDK 验证闭环。

## 6. 多设备、任务队列和设备发现问题

### 6.1 同设备并发可能互相干扰

**问题**

如果同一台设备同时安装、启动或处理多个任务，会争用前台 Activity、安装器、文件目录和 ADB 操作。

**处理**

建立按设备隔离的队列：

- 同一设备严格串行；
- 不同设备允许并行；
- 每个 `deviceRun` 有独立 ID、序列号、日志、检查结果和输出。

**状态：已解决并验证。** 队列测试覆盖串行和跨设备并行。

### 6.2 单个 Worker 异常污染整批任务

**历史风险**

某个设备的 Worker 抛异常时，可能中断同设备后续任务，或者错误修改其他设备运行状态。

**处理**

- 异常只失败当前 `deviceRun`；
- 同设备队列继续执行下一项；
- 回退失败只更新目标运行；
- 一个设备失败不污染其他设备结果；
- 任务进度和通过率从各设备运行聚合。

**状态：已解决并验证。**

### 6.3 取消任务后仍可能继续执行或点击

**风险**

任务取消后，排队任务、ADB Worker 或安装弹窗控制器若继续工作，可能安装 APK、点击系统对话框或写回错误状态。

**处理**

- 从队列中移除尚未执行的运行；
- 通知正在执行的 Worker；
- 取消后的 Worker 晚到更新被忽略；
- 安装器监控和 UI 点击立即停止；
- 受影响的设备运行标记为 `blocked`。

**真实记录**

当前数据库中有 1 个任务在约 79% 时取消，代码为 `TASK_CANCELLED`，对应设备运行被标记为 `blocked`。

**状态：已解决并验证。** 真实记录和自动化测试均有证据。

### 6.4 ADB 设备状态解析不完整

**历史问题**

- 未明确区分 `online`、`offline`、`unauthorized`；
- 对离线或未授权设备读取 `getprop`，可能导致误判；
- 属性读取失败时可能填入看似真实的值；
- 重复发现可能产生重复设备；
- 历史设备 ID 与新发现记录可能不一致。

**处理**

- 显式解析三类状态；
- 只对已授权在线设备读取属性；
- 读取失败返回 `unknown`；
- 重复注册幂等；
- 保留历史 Magic V3 设备 ID；
- 新发现记录映射回已注册设备。

**状态：已解决并验证。**

### 6.5 vivo 上“包不存在”被误判为 ADB 安装失败

**根因**

vivo 对查询未安装包返回了 OEM 特有输出，旧代码把它当成 ADB 命令执行失败，而不是正常的“当前未安装”。

**处理**

将“包不存在”与真正的 ADB 命令失败分开处理。

**状态：已解决并验证。** `adb-client.test.ts` 有覆盖。

### 6.6 早期 HONOR 设备离线

备份数据库中有 4 个 2026-07-29 的真实失败：

```text
phase: validating_device
failureCode: DEVICE_OFFLINE
message: 荣耀真机未连接或 ADB 状态异常
```

之后同一 HONOR 设备已有 3 个通过任务，说明 USB/ADB 连接已恢复。

**状态：历史故障，已恢复。** 这是设备连接/运行环境问题，不是算法失败。

## 7. Android OEM 无人值守安装与权限问题

### 7.1 初版“自动安装”实际仍依赖人工点击

**现象**

早期任务可以通过，但平台日志显示自动处理的弹窗数量为 0。实际是用户在 vivo/HONOR 手机上手工点击了安装确认。

**根因**

- 不同 Android/OEM 的 `dumpsys window windows` 输出不同；
- 前台 package/activity 解析失败；
- 真实安装器包名和 Activity 与通用假设不一致；
- UI Automator XML 获取和解析不完整；
- OEM 安装页面没有对应的严格识别规则。

**处理**

拆分出独立的 `AndroidAppPreparer` 和 `SystemDialogController`，并实现：

- vivo、HONOR、OPPO 的严格 UI Profile；
- 使用真实 UI XML fixture 回归测试；
- 点击坐标只从 XML 节点 `bounds` 计算，不使用固定屏幕坐标；
- 已知安装器页面未加载完成时给予等待期；
- 对未知或超时页面保存 XML、截图和 window diagnostics；
- 不点击不明确的通用按钮。

**状态：已解决并验证。** 多款真实设备后续运行通过。

### 7.2 HONOR 权限已授予，却被误报为未授予

**现象**

`pm grant` 已成功，但平台报告：

```text
RUNTIME_PERMISSION_NOT_GRANTED
```

**根因**

旧代码依赖以下并非所有 OEM 都支持的命令：

```text
cmd package check-permission
pm check-permission
```

HONOR 上验证命令不兼容，导致“验证方式失败”被误判为“权限没有授予”。

**处理**

改用 `dumpsys package`，检查对应权限的 `granted=true`，不再依赖 HONOR 不支持的检查命令。

**状态：已解决并验证。**

### 7.3 vivo 查询未安装包导致准备阶段失败

该问题与 6.5 相同，但在三设备回归中表现为 vivo 准备失败：应用尚未安装时的正常 OEM 输出被当作 ADB 错误。

**处理**

区分包缺失与命令异常。

**状态：已解决并验证。**

### 7.4 安全锁屏自动化风险

**安全要求**

平台不能绕过 PIN、密码、图案或生物识别锁屏。

**处理**

- 唤醒设备；
- 只尝试无密码解锁；
- 如果仍存在安全锁屏，拒绝继续自动化；
- 不尝试破解或绕过系统安全。

**状态：已解决并有测试覆盖。**

### 7.5 已知安装器页面过早被判定为未知

**现象**

尤其在 vivo 上，页面仍处于风险扫描或内容加载过程中，按钮和文案尚未完全出现，旧逻辑立即返回 `INSTALL_DIALOG_UNRECOGNIZED`。

**处理**

对已知且受信任的安装器 package/activity 增加加载宽限期，允许 UI 完整渲染后再匹配。

**状态：已解决并验证。**

### 7.6 UI 自动化误点击风险

**处理原则**

- vivo 风险页面必须同时匹配应用身份和完整关键特征；
- HONOR 必须先处理风险勾选框，再点击继续；
- “继续”“确定”等通用文字不能单独构成授权依据；
- Morpho 身份和至少两个页面特征同时成立才允许执行；
- 安装流程结束后，不能继续沿用旧的身份识别证据；
- `bounds` 为空或非法时拒绝点击；
- OEM `windows` 子命令缺失焦点时，回退到完整 `dumpsys window`；
- 已更新的系统安装器即使 APK 位于 `/data/app`，也通过系统身份而非简单路径判断是否可信。

**状态：已解决并有多组安全回归测试。**

## 10. 输出、报告和视频播放问题

### 10.1 多设备输出容易混用

**风险**

如果输出只按 `taskId` 保存，多台设备会覆盖或引用错误视频。

**处理**

输出与 `deviceRunId` 绑定，报告按设备展示独立输出、日志、截图和检查结果。

**状态：已解决并验证。**

### 10.2 报告视频不能稳定播放或拖动

**处理**

实现 HTTP Range：

- 无 `Range`：返回完整文件；
- 合法 `Range`：返回 `206 Partial Content`；
- 越界或非法 `Range`：返回 `416 Range Not Satisfiable`；
- 独立下载端点；
- 缺少 output/logcat/screenshot 时返回明确 404。

**状态：已解决并有自动化测试。**

### 10.3 输出证据不完整

**处理**

输出记录增加：

- 文件大小；
- SHA-256；
- 每设备输出定位；
- 日志、截图、检查结果。

Android 平台载体还可检查：

- 输出存在且非空；
- 能开始播放/出现首帧；
- 连续播放时长；
- 旋转后继续播放；
- 超时和明确失败代码。

**状态：部分解决。**

### 10.4 “任务通过”的质量语义仍然过宽

Morpho 协议当前主要证明：

- 执行链路完成；
- 找到了输出；
- 输出非空；
- 保存了大小和 SHA-256。

这并不能证明：

- MP4 容器完全合法；
- 视频流可完整解码；
- 时长、分辨率、帧率符合预期；
- 没有黑屏、绿屏、花屏或严重丢帧；
- 稳像算法质量达到验收标准。

**状态：P0 未解决风险。** 需要引入 ffprobe、解码抽检、流元数据、时长容差、黑/绿帧和质量指标。

> 当前 `output.mp4` 成功只能证明该 SDK、设备和视频组合下的已实现执行链路通过，不能被描述为完整的 SDK 算法质量认证或生产发布门禁。

## 11. 任务删除、文件安全和备份问题

### 11.1 删除任务可能误删共享制品或造成数据库/文件不一致

**风险**

- 删除运行中的任务；
- 误删其他任务仍引用的 APK/视频；
- 数据库已经删除，但文件删除中途失败；
- 路径越界删除；
- 并发删除同一任务；
- 删除后没有审计。

**处理**

新增 `TaskDeletionService`：

- 只允许删除终态任务；
- 拒绝 queued/running；
- 只级联目标任务的数据；
- 保留仍被引用的共享制品；
- 只有无引用制品才允许删除；
- 使用路径 allowlist；
- 先移动到 `.trash/delete-{uuid}`；
- 在数据库事务中执行删除；
- 事务失败时恢复文件；
- 任务目录缺失只记录警告，不破坏 DB；
- 非法 ID 直接拒绝；
- 并发删除串行化；
- 任务删除后保留删除审计；
- 路由对未知异常返回稳定 500，不泄漏内部细节；
- Mock 删除不影响无关 localStorage 数据。

**验证**

- 自动化测试覆盖核心安全规则；
- 当前有 15 条真实删除审计；
- 审计未记录清理警告。

**状态：已解决并验证。**

### 11.2 直接复制 SQLite 可能遗漏 WAL 数据

**风险**

运行中的 SQLite 使用 WAL 时，直接复制主数据库文件可能得到不完整备份。

**处理**

备份脚本改为：

- 使用 Node SQLite 在线备份；
- 先写入 `.incomplete-*` 临时目录；
- 完成后原子重命名；
- 生成包含表计数的 manifest；
- 记录恢复说明。

**状态：已解决。** 当前已有两份 2026-07-30 的备份可用于历史分析。

## 12. 当前尚未解决的风险和技术债

## 12.1 P0：必须优先处理

### P0-1：仓库没有 Git 基线

当前 `main` 分支没有任何 commit。

**影响**

- 无法可靠回滚；
- 无法区分每次修复；
- 无法进行规范 Code Review；
- CI/CD、版本发布和变更审计没有可信起点；
- 当前这份 Bug 总结也无法用 commit 逐条佐证。

**建议**

立即完成敏感文件检查、建立首个基线提交，并从此采用小步提交、分支和 PR。

### P0-2：通过语义不足以代表视频质量通过

见 10.4。需要建立 ffprobe/解码/视觉质量门禁。

### P0-3：真实 SDK Bridge 缺失

平台载体 APK 缺少真实 `VendorSdkBridgeImpl`，真实 SDK 初始化链路未闭环。

### P0-4：本地网络暴露且没有认证

API 自身可能只绑定 loopback，但 Vite 当前绑定 `0.0.0.0` 并代理 `/api`。同一局域网内的其他用户可能通过前端开发服务器间接访问：

- 上传；
- ADB 设备操作；
- 取消任务；
- 删除任务等接口。

**建议**

默认只监听 loopback；如需共享模式，必须增加身份认证、RBAC、审计、TLS 和明确的共享开关。

### P0-5：APK 被当作可信可执行输入

当前主要按包名/协议元数据判断是否支持，没有：

- 签名证书白名单；
- 来源白名单；
- APK 哈希批准清单；
- 恶意行为隔离。

攻击者可伪造受支持包名，诱导平台把恶意 APK 安装到真机。

**建议**

至少校验签名证书、来源和哈希；设备应隔离在专用测试环境。

### P0-6：multipart 请求级限制过宽

全局上传上限按视频最大值约 4 GiB 设置，而 APK 业务上限约 1 GiB，往往要接收大量数据后才拒绝；上传限制错误也未统一返回 413。

**建议**

按制品类型设置请求级上限，并收紧 parts、fields、header 等限制，统一返回 `413 Payload Too Large`。

### P0-7：没有数据生命周期和磁盘保护

当前 `data/` 已约 3.5 GB，尚无：

- TTL；
- 总配额和用户配额；
- 磁盘低水位拒绝；
- 内容去重；
- 孤儿文件清理；
- 自动备份轮转；
- 证据保留策略。

**建议**

先实现磁盘水位保护和可配置保留期，再做哈希去重、孤儿扫描和备份轮转。

## 12.2 P1：进入稳定测试服务前应处理

1. **队列只在内存中**：服务重启后不能恢复 lease、attempt 和正在等待的任务。
2. **没有 Run/Attempt 分层**：重试只能创建新任务，会扭曲历史和通过率。
3. **重启中的任务直接失败**：当前会被标为 `SERVICE_RESTARTED`，不能自动恢复。
4. **没有冻结执行清单**：未完整记录 SDK 版本、计划/协议版本、服务构建、设备系统快照和运行时配置。
5. **数据库迁移不正式**：依赖 `CREATE IF NOT EXISTS` 和列检查，缺少可版本化 migration。
6. **同步 SQLite 可能阻塞 Fastify**：`DatabaseSync` 在更高并发下存在事件循环阻塞风险。
7. **大文件职责集中**：`adb.ts`、`database.ts`、`server.ts` 仍然过大。
8. **创建任务和上传不幂等**：网络重试可能生成重复制品或重复任务。
9. **证据不是一级模型**：当前主要靠目录和路由组织，缺少 Evidence 表、类型和生命周期。
10. **缺少完整 AdbWorker Fake ADB 端到端测试**。
11. **缺少浏览器级 Playwright 测试**。
12. **缺少 Android instrumentation 测试**。
13. **设备断连/恢复仍依赖真机人工验收**。
14. **前后端重复定义领域类型**，长期存在漂移风险。

## 12.3 P2：扩展和性能规划

1. 执行页每秒轮询；规模扩大后再评估 SSE/WebSocket。
2. 前端产物约 1.32 MB，Vite 提示 chunk 超过 500 kB，应做路由懒加载和代码分包。
3. iOS/HarmonyOS 当前主要是页面或类型占位，真实执行器仍是 Android 专用。
4. 当前设备队列只适合单控制进程，多实例会产生所有权问题。
5. `node:sqlite` 在不同 Node 版本中的稳定性/实验性状态需要锁定运行环境。
6. 尚无正式的自动重试语义和失败分类策略。
7. 尚无设备基线、清理和恢复策略。
8. 尚无证据保留期共识。
9. 尚无用户/租户配额和多用户审计身份，`deleted_by` 当前为 `local-user`。

## 15. 建议处理优先级

### 第一优先级：先保护代码、设备和数据

1. 检查敏感文件并创建 Git 基线提交；
2. Vite 默认改为 loopback；
3. 对支持 APK 增加签名证书和哈希白名单；
4. 增加磁盘低水位拒绝和最基本的 TTL；
5. 按 APK/视频分别设置 multipart 请求级限制。

### 第二优先级：提高“通过”结果可信度

1. 使用 ffprobe 验证容器、视频流、时长、尺寸和帧率；
2. 做完整或抽样解码；
3. 增加黑屏、绿屏、静帧和严重异常检测；
4. 冻结每次运行的 SDK、协议、服务和设备环境；
5. 与业务方书面确认“兼容性通过”和“算法质量通过”的区别。

### 第三优先级：提高服务可恢复性

1. 持久化队列、租约和 Attempt；
2. 设计重试语义；
3. 服务重启后恢复或明确接管任务；
4. 正式化数据库 migration；
5. 增加上传和创建任务的幂等键。

### 第四优先级：扩大自动化覆盖和可维护性

1. AdbWorker Fake ADB 端到端测试；
2. Playwright 浏览器流程测试；
3. Android instrumentation 测试；
4. 拆分 `adb.ts`、`database.ts`、`server.ts`；
5. 统一前后端领域类型；
6. 前端懒加载和代码分包。

## 16. 最终结论

项目已经从一个前端 Mock/方案阶段，演进为可连接多台 Android 真机、执行真实 ADB 流程、适配 Morpho APK、自动处理多个 OEM 安装/权限页面、收集输出和证据、生成报告并安全删除任务的本地云测试平台。

本轮问题处理中最重要的技术转折是：

1. **不再把所有 APK 套进一个硬编码协议，而是使用可识别、可拒绝的 APK Protocol；**
2. **确认早期 vivo 可疑输出的主要原因是 Worker/Morpho 协议不匹配，而非直接判定算法不兼容；**
3. **将 OEM 弹窗自动化从泛化点击改为严格身份与特征匹配，宁可安全失败，也不误点未知系统页面；**
4. **建立按设备隔离的运行、队列、输出和失败模型；**
5. **通过删除服务和在线备份补上了基本数据安全。**

但是，目前仍不应把平台描述为完整的生产级质量门禁。最大的原因是：仓库没有 Git 基线、真实 SDK Bridge 尚未接入、输出质量校验仍较浅、API/开发代理缺少认证与隔离、APK 信任和数据生命周期尚未建立。

因此，更准确的项目定位是：

> **已经具备真实 Android 多设备兼容性执行能力的本地测试平台原型/内部工具；主执行链路可用，OEM 适配和安全兜底已有较强基础，但在版本治理、安全、数据生命周期、可恢复调度和视频质量门禁方面仍需继续工程化。**
