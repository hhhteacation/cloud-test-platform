# SDK 云测试平台：官方文档架构证据

> 研究对象：本地 Android APK + MP4 真机兼容性测试平台（React/Vite、Fastify 5、`node:sqlite`/SQLite、按设备内存队列、ADB 执行、文件证据）。  
> 研究边界：只采用官方文档、标准、官方项目仓库或第一方资料；不采用博客和二手解读。  
> 核对/访问日期：**2026-07-31（Asia/Shanghai）**。若官方页面没有给出更新时间，下文明确写“未标注”，不以访问日期冒充更新时间。  
> 优先级：**P0**＝当前暴露面或正确性阻断；**P1**＝进入可靠单节点/共享实验室前必须完成；**P2**＝达到规模或多平台触发条件后演进。

## 0. 结论先行

1. **`pnpm dev` 当前确实形成了局域网到本地 API 的间接通路。**`vite --host 0.0.0.0` 让 Vite 监听所有地址；Vite 又把 `/api` 代理到宿主机的 `127.0.0.1:3000`。因此 Fastify 只绑定 loopback 只能阻止局域网客户端**直接**访问 3000，不能阻止其通过 Vite 5173 **间接**访问 API。结合当前 API 无认证且能上传、安装 APK、调度 ADB、取消/删除任务，这是 **P0**。
2. **Android 无法承诺“插线后全程零人工”。**新 ADB 主机首次连接需要设备解锁并确认 RSA 调试授权；`adb install -g`/`pm grant`只覆盖运行时权限，不覆盖特殊权限、受限设置和 OEM 自定义确认；App-specific external storage 无需存储权限但会随卸载删除，且 Android 11 起其他应用不能访问该目录。应把授权、Developer options、特殊权限、锁屏/OEM 弹窗做成设备准入与预检，而不是埋在通用 Worker 中假定必然成功。
3. **SQLite WAL 适合当前单机模块化单体，但不是“多写者无限并发”。**WAL 允许读写并行，但任一时刻仍只有一个 writer；WAL 依赖同主机共享内存，不能直接放网络文件系统。长读事务会阻碍 checkpoint、导致 WAL 增长。当前在线 `node:sqlite backup()` 方向正确；禁止在数据库打开时只复制主 `.sqlite` 文件。
4. **`node:sqlite` 在当前 Node 24 文档中仍是 Release candidate（Stability 1.2），且 `DatabaseSync` API 同步执行。**应锁定受支持 Node 版本、做升级回归；事务必须短，避免同步数据库等待阻塞 Fastify 事件循环。多 Runner/高写并发不是继续堆同步 SQLite 调用的理由。
5. **当前 multipart 流式落盘与随机服务端文件名是正确基础，但限额和错误映射仍需收紧。**插件全局 `fileSize` 取 APK/视频上限最大值，使 APK 最多可能先接收约 4 GiB 后才被业务层按 1 GiB 拒绝；应按路由/`kind`设置限额，并把插件超限错误映射为 413。MP4 扩展名/MIME 均是客户端输入，不足以证明内容；APK 也应增加签名证书/来源策略。
6. **共享访问不能只“加一个登录页”。**必须在每个请求和每个对象上校验授权，默认拒绝；所有 Task、Run、Artifact、Evidence、Device 与文件路径都要带租户/所有者边界；审计记录 actor、tenant、action、object、outcome、request/trace id，且不记录 token、密码和敏感数据。
7. **任务进度首选从轮询演进到 SSE，而不是直接 WebSocket。**进度、阶段和日志尾流主要是服务端到浏览器单向推送；SSE 原生具备事件 ID、断线重连语义。命令仍走普通 HTTP。只有远程交互控制、双向实时输入等明确需求出现时才采用 WebSocket。
8. **iOS 与 HarmonyOS 应复用领域模型，不复用 ADB 语义。**iOS 真机需要 macOS/Xcode、签名/注册设备、首次 Developer Mode 人工确认，并可用 `xcodebuild` 的 `build-for-testing`/`test-without-building` 与 XCTest；OpenHarmony 官方 hdc 可列举/指定设备、安装 HAP、传文件、执行 shell、收集 hilog。它们应成为独立 Runner/Adapter。
9. **媒体“完整性”必须分层命名，不能把 `ffprobe` 探测成功写成“视频完整可播放”。**`ffprobe`能报告容器、流、包/帧计数和探测错误；全文件可解码性要用 `ffmpeg`实际解码到 null muxer，并把解码错误转成失败；即便全解码成功，也不证明无黑屏/绿屏、音画同步正确或主观质量合格。

## 2. SQLite WAL、并发、备份、迁移与 `node:sqlite`

| 官方事实 | 对本项目的含义 | 建议 | 优先级 | 来源（更新时间/版本；访问日期） |
|---|---|---|---|---|
| WAL 中 reader 与 writer 可并行，但同一时刻仍只有一个 writer；默认自动 checkpoint 阈值是 1000 页。长 reader 可能使 checkpoint 无法完成并让 WAL 持续增长。 | WAL 能支持当前少量 API 读 + 单调度进程写，但不能等价为多 Runner 多写者数据库。报告查询的长事务也会影响磁盘增长。 | 保持事务极短；设置/观测 `busy_timeout`、WAL 字节数、checkpoint 耗时与 busy 结果；分页查询，避免长时间持有 read transaction。 | P1 | [SQLite：Write-Ahead Logging](https://sqlite.org/wal.html)（页面未标注统一更新时间；内容含 2025-07-31 WAL-reset 修复说明；2026-07-31） |
| WAL 要求所有进程在同一主机并共享 `-shm`，不能工作在网络文件系统；`-wal` 是数据库持久状态的一部分，复制/移动数据库时把它与主文件分离可能丢失已提交事务或损坏数据库。 | 不能通过把 `data/` 挂 NFS 就获得多 Runner 数据层；也不能热复制单个 `cloud-test.sqlite` 当备份。 | SQLite 与 WAL/SHM 保持本机盘；共享服务阶段通过正式 DB/队列或单一 DB 服务访问。备份只走在线 Backup API或停库后成组复制。 | P0 | [SQLite：WAL disadvantages / persistence](https://sqlite.org/wal.html)（未标注；2026-07-31） |
| SQLite 任一时刻仅允许一个写事务；`BEGIN IMMEDIATE`会立即尝试启动写事务，失败时返回 `SQLITE_BUSY`。 | 设备 lease 的 claim 可在单机 SQLite 事务里实现，但必须有原子条件更新/CAS；仅靠内存 `Map`不能让第二进程安全接管。 | `queued → allocated`、设备 lease 和 fencing token 在单个短事务内完成；检查受影响行数；显式处理 BUSY 与退避。 | P1 | [SQLite：Transaction](https://sqlite.org/lang_transaction.html)（页面未标注；2026-07-31） |
| Online Backup API 可在源数据库被其他客户端访问时创建一致快照；Node `backup()`封装了该 API。 | 当前 `scripts/backup-cloud-test-data.mjs` 使用 `node:sqlite backup()`是正确方向，优于复制单一主文件。文件制品还需与 DB 快照建立一致性边界。 | 保留在线 DB 备份；备份 manifest 记录 DB snapshot 时间、制品清单和哈希；定期在空目录执行恢复演练，而不只验证“命令成功”。 | P1 | [SQLite：Online Backup API](https://sqlite.org/backup.html)（未标注；2026-07-31）；[Node.js v24 `sqlite.backup`](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#sqlitebackupsource-path-options)（v24 文档；2026-07-31） |
| `PRAGMA user_version`是留给应用使用的整数版本字段；SQLite 不自行使用它。 | 当前 `CREATE IF NOT EXISTS + ensureColumns()`只能处理简单增列，无法表达有序迁移、校验、失败回滚和不可逆数据变换。 | 增加 `schema_migrations(version,name,checksum,applied_at)`；在事务内按顺序迁移，并同步维护 `user_version`；启动时拒绝未知高版本。 | P1 | [SQLite：PRAGMA user_version](https://sqlite.org/pragma.html#pragma_user_version)（未标注；2026-07-31） |
| Node 24 文档把 `node:sqlite`标为 **Stability 1.2 — Release candidate**；`DatabaseSync`的 API 是同步执行。模块从 v22.5.0 引入，v22.13/v23.4 起不再需要实验标志；`backup()`在 v22.16/v23.8 加入。 | 项目本机 Node v24.18.0 可用，但 API 成熟度仍不是 Stability 2。同步 SQL/锁等待会阻塞 Fastify 所在事件循环。 | 声明并锁定 Node 支持矩阵；升级 Node 前跑 DB/备份/恢复测试。API 线程只做短查询；重报表、校验或高并发调度迁到 Worker/独立服务。 | P1 | [Node.js v24：SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)（文档显示 Stability 1.2；2026-07-31） |

**SQLite 继续适用的边界：**单主机、单调度器、有限写并发、短事务、任务事实持久化并可恢复。出现多个控制面实例竞争写入、多个远程 Runner 同时 claim、数据库位于网络文件系统、大量日志逐条入库，或 checkpoint/WAL/`SQLITE_BUSY`持续异常时，再评估 PostgreSQL/专业队列；不应仅因为“未来服务化”提前替换。这里的机制边界来自 SQLite 官方文档，但具体吞吐量和迁移阈值是项目决策，必须以压测与运行指标确定，不能写成 SQLite 官方容量保证。

## 3. Fastify 5 multipart 与文件上传安全

| 官方事实 | 当前含义/风险 | 建议 | 优先级 | 来源（更新时间/版本；访问日期） |

## 5. Vite `host`/`proxy`：当前 LAN 暴露结论

### 5.1 可核验事实

- Vite 官方定义：`server.host`设为 `0.0.0.0`或 `true`会监听**所有地址，包括 LAN 和公网地址**；CLI 提供 `--host [host]`参数。  
  来源：[Vite server.host](https://vite.dev/config/server-options.html#server-host)、[Vite CLI](https://vite.dev/guide/cli.html)（页面更新时间未标注；访问 2026-07-31）。
- Vite 官方定义：`server.proxy`把 key 匹配的请求代理到指定 target；匹配代理规则的请求不会再由 Vite转换。  
  来源：[Vite server.proxy](https://vite.dev/config/server-options.html#server-proxy)（未标注；访问 2026-07-31）。
- 项目事实：`pnpm dev`中的 Web 命令是 `vite --host 0.0.0.0`；`vite.config.ts`把 `/api`代理到 `http://127.0.0.1:3000`；Fastify 自身监听 `127.0.0.1:3000`。

### 5.2 判断

**是，会间接暴露。**在主机防火墙、路由和 Vite `allowedHosts`允许访问的前提下，局域网客户端请求：

```text
http://开发机LAN-IP:5173/api/...
        ↓
Vite（监听 0.0.0.0:5173）
        ↓  server.proxy 从开发机本机发起
Fastify（127.0.0.1:3000）
```

`127.0.0.1`只限制谁能直接连接 Fastify；Vite 本身是一个可被 LAN 连接的代理客户端，所以该限制不会穿透代理链。`allowedHosts`主要缓解 Host/DNS rebinding，不是身份认证，也不会阻止按 IP 访问这一事实。

### 5.3 决策

| 模式 | 必须满足 | 优先级 |
|---|---|---|
| 默认本地模式 | 删除 `--host 0.0.0.0`或显式 `--host 127.0.0.1`；API 继续 loopback；启动日志明确“仅本机”。 | **P0，立即** |
| 临时 LAN 演示 | 不复用真实 ADB/真实数据；至少防火墙 allowlist、临时凭证、最小权限、上传/请求限流；演示结束关闭。 | P0 |
| 共享实验室 | 受信反代/TLS、认证、对象级授权、审计、CSRF/Origin 策略、配额、速率限制、专用设备；Vite dev server 不作为共享入口。 | P1 Gate |

## 6. 从 HTTP 轮询演进到 SSE / WebSocket

| 规范事实 | 架构含义 | 建议 | 优先级 | 来源（更新时间；访问日期） |
|---|---|---|---|---|
| HTML Living Standard 定义 `EventSource`连接 `text/event-stream`；`id`字段更新客户端的 last event ID，连接重建时若该值非空，用户代理在请求中设置 `Last-Event-ID`；连接关闭后通常会自动重连，`retry`字段可更新重连时间。 | 任务状态、phase、progress、检查结果和日志尾流天然是单向更新。事件 ID 可作为续传游标，但服务器仍必须保留可重放事件或让客户端在 gap 后重新获取权威快照。 | 保留 `GET /tasks/:id`快照，新增 `/tasks/:id/events` SSE；事件按 task/attempt 单调编号并设有界保留；重连从 `Last-Event-ID`续传，游标过旧/断档时返回 gap 事件并重拉快照；命令仍用 HTTP。 | P2（规模触发）；设计 P1 | [WHATWG HTML：Server-sent events / Last-Event-ID](https://html.spec.whatwg.org/multipage/server-sent-events.html)（Living Standard，页面标注 2026-07-20；2026-07-31） |
| 原生 EventSource 构造参数只有 URL 与 `withCredentials`选项，没有任意 header 参数。 | 如果共享模式只接受 `Authorization: Bearer`，原生 EventSource 不能直接复用该 header。把长期 token 放 query string又会泄漏到历史/日志。 | 同源安全 Cookie + CSRF/Origin 策略，或 fetch streaming/短期一次性 ticket；事件路由同样执行对象级授权。 | P1（共享模式） | [WHATWG HTML：The EventSource interface](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface)（Living Standard；2026-07-31） |

**触发条件：**当前少量本地用户可继续轮询；当并发打开的任务详情、日志尾流或 API 读放大成为可观测问题时上 SSE。建议先消除同页面重复的 1 秒/2 秒轮询并增加退避、页面不可见暂停和 ETag/版本条件读取。

## 7. 多设备队列、重启恢复与可观测性

### 7.1 一手机制约束

- AWS SQS 官方说明 standard queue 采用 **at-least-once delivery**，同一消息可能重复投递；visibility timeout 期间消息对其他 consumer 暂时不可见，但需要延长、删除或在超时后重投。官方明确建议 consumer 设计为幂等。该机制不是要求采用 AWS，而是一个可核验的可靠队列参照。  
  来源：[Amazon SQS：At-least-once delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)、[Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)（页面更新时间未标注；访问 2026-07-31）。
- OpenTelemetry 官方把 traces、metrics、logs定义为可观测信号；W3C Trace Context 标准定义 `traceparent`/`tracestate`用于跨服务传播追踪上下文。  
  来源：[OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/)（未标注；2026-07-31）、[W3C Trace Context](https://www.w3.org/TR/trace-context/)（W3C Recommendation 2021-11-23；2026-07-31）。
- Prometheus 官方命名指南提醒：标签的每个组合都会形成新时间序列，不能对无界高基数字段过度使用 labels。  
  来源：[Prometheus：Metric and label naming](https://prometheus.io/docs/practices/naming/)（未标注；2026-07-31）。

### 7.2 对当前队列的落地建议

当前“同设备串行、不同设备并行”是正确不变量；问题是 Lane 在内存，重启时 running 被直接标失败。建议先在 SQLite 增量加入：

```text
run_attempts(id, run_id, attempt_no, status, phase, worker_id,
             lease_id, fencing_token, heartbeat_at, started_at, finished_at,
             failure_code, failure_message)

device_leases(device_id, attempt_id, owner, acquired_at, expires_at, fencing_token)
```

1. 事务内 claim queued Run 并创建 Attempt/Lease；同一设备最多一个未过期 lease。
2. Worker 周期心跳；长 ADB 操作前后持久化 phase。
3. 重启只把**过期** lease 置 interrupted；先做设备/远端目录探测和清理，再按显式策略创建新 Attempt，绝不覆盖旧 Attempt 证据。
4. 允许重复调度，因此安装、目录创建、输出回收和终态写入必须幂等；终态更新用 attempt id + fencing token 做 CAS，拒绝晚到 Worker。
5. 多 Runner 时采用“控制面 + 每主机 Device Agent”；serial/USB 是 agent 本地资源，调度按 platform/capability/agent 路由，不让中央 API 直接假定能访问所有 USB。

### 7.3 最小可观测性

- **Metrics（低基数）**：`queue_depth{platform,status}`、最老 queued age、active attempts、online/ready devices、lease expirations、retries、phase duration histogram、upload bytes/duration、HTTP status、WAL bytes/checkpoint busy、磁盘剩余量。不要把 `task_id`、`run_id`、完整 serial 作为 Prometheus label。
- **Structured logs（可含高基数关联字段）**：`request_id/task_id/run_id/attempt_id/device_id/agent_id/platform/phase/error_code`。
- **Traces**：HTTP create → scheduler claim → agent → install/push/launch/wait/pull/validate；跨服务传播 `traceparent`。
- **Health 分层**：liveness 只回答进程是否活着；readiness 回答 DB 可写、调度可接单、磁盘未低水位；设备 online/ready 独立呈现，不能一台设备离线就杀死服务。

优先级：Attempt/Lease/原子状态转移与重启恢复 **P1**；完整 OTel 导出可在远程 Runner 前完成 **P1/P2**。

**可行性结论与边界：**Apple 一手资料足以证明“构建一次、按 destination 在设备矩阵执行 XCTest”的 Adapter 方向可行；但不能据此承诺和 Android 相同的任意 IPA 安装、跨主机环境或首次接入无人值守体验。macOS/Xcode 版本、签名身份、App ID、provisioning profile、注册设备、Trust/Developer Mode 都是 iOS Runner 的显式前置条件。

**建议：**先做一条 macOS Runner 技术验证：固定签名测试 App + XCTest plan → `build-for-testing` → 两台注册设备 `test-without-building` → 收集 `.xcresult`、截图和日志。通过后再定义通用 iOS Artifact API，避免照搬 APK Protocol。

### 8.2 HarmonyOS / OpenHarmony hdc

OpenHarmony 官方 hdc 仓库确认：hdc 是开发机 client + 开发机 server + 设备 daemon 的连接调试工具，PC 端支持 Windows/Linux/macOS；命令包括 `list targets`、`-t <device-id>`、`install <package>`、`file send`、`file recv`、`shell`、`hilog`和端口转发。这足以证明可以建立与 ADB 对等但语义独立的设备 Adapter。  
来源：[OpenHarmony 官方 `developtools_hdc` README_zh](https://gitee.com/openharmony/developtools_hdc/blob/master/README_zh.md)（该文件最近提交 2025-03-20；[对应官方提交](https://gitee.com/openharmony/developtools_hdc/commit/6720a340fe0a6892e999b1e82a9d4cdaba1d8dff)；访问 2026-07-31）；[华为开发者：hdc](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/hdc)（动态页面未标注统一更新时间；访问 2026-07-31）。

**可行性结论与边界：**OpenHarmony/Huawei 一手资料足以证明 hdc 具备设备发现/选择、安装、文件通道、shell 与日志采集等 Adapter 基础能力；但这不是对所有商业 HarmonyOS 设备、SDK/hdc 版本、签名/权限策略和无人值守体验的一致性保证。

**建议：**实现 `HarmonyDeviceProvider/HdcExecutor/HarmonyEvidenceCollector`，显式传 `-t device-id`，使用 HAP/APP 与 hilog 语义；不要复用 APK、Intent、Android permission 或 `/Android/data`路径。商业 HarmonyOS 与 OpenHarmony、SDK/hdc 版本之间仍需一次真实设备 spike 后再承诺完整自动化范围。

## 9. 建议决策与实施顺序

| 顺序 | 决策/工作包 | 验收条件 | 优先级 |
|---:|---|---|---|
| 1 | 关闭默认 LAN 控制面 | `pnpm dev`默认 Web/API 仅 loopback；从另一台 LAN 主机不可访问；共享模式有独立显式配置。 | P0 |
| 2 | 上传与可执行输入治理 | 按 kind 限额、413、临时隔离/清理、MP4 结构探测；严格模式执行全解码；APK 签名证书策略、磁盘低水位拒绝。 | P0 |
| 3 | Android readiness/Protocol 版本化 | 首次 ADB 授权、普通/特殊/受限权限、安装数据策略、app-specific 目录生命周期均可预检并进入 Manifest。 | P0 |
| 4 | SQLite 运维基线 | 正式 migration、busy/checkpoint/WAL 指标、在线备份清单、恢复演练；Node 版本矩阵固定。 | P1 |
| 5 | Attempt + Lease | queued 持久；running 有 heartbeat/lease/fencing；重启与重复投递产生可解释 Attempt，不覆盖历史。 | P1 |
| 6 | 共享实验室安全 Gate | 身份、对象级授权、tenant 全链路、审计、TLS/反代、配额/限流全部到位后才开放 LAN。 | P1 |
| 7 | SSE | 快照 + event id + reconnect/gap recovery；授权与连接清理通过测试；命令仍为 HTTP。 | P2/规模触发 |
| 8 | 平台 Adapter spike | iOS 完成签名 XCTest 真机闭环；Harmony 完成 hdc 指定设备、安装、文件、hilog 闭环，再承诺平台支持。 | P2 |

## 10. 最终架构判断

当前最合适的形态仍是**本地优先的模块化单体**，不是立即微服务化：SQLite WAL、单进程 Fastify 和每设备串行 Lane 足以支撑可信 Android 闭环。下一步的真正 seam 是 `Attempt/Lease`、`Platform Executor`、`Artifact/Evidence Store`、`Identity/Tenant Context` 与结构化事件，而不是先换数据库或先增加平台入口。

唯一必须立即改变的外部边界是：**默认不把无认证 Vite 代理暴露给局域网。**在这条 P0 完成前，“Fastify 只监听 127.0.0.1”不能作为安全结论。
