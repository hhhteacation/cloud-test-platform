## 1. 记录目的

本记录用于区分三种容易被混淆的结果：

1. **定向测试通过**：改变所覆盖的测试行为通过；
2. **提交门禁通过**：该提交自己的完整测试、类型检查、构建、差异检查和干净状态均通过；
3. **真机 Gate 通过**：在明确记录代码身份的真实设备上重复运行并通过。

只有第 2 项成立，提交才可以作为独立的自动化稳定化节点；第 3 项尚未在本轮完成。

## 2. 统一门禁命令


## 4. `794d9cf` 的失败证据

`794d9cf` 将 `AdbDeviceClient.stat/exists/isPackageRunning` 的结果改为结构化观察结果 `AdbObservation<T>`，但 `apps/api/src/adb.ts` 在该提交中仍把结果当作普通数字或布尔值比较。

API TypeScript 的实际错误包括：

```text

apps/api/src/adb.ts(367,11): TS2365
apps/api/src/adb.ts(370,11): TS2367
apps/api/src/adb.ts(625,11): TS2365
apps/api/src/adb.ts(653,13): TS2365
```

这不是测试用例失败，而是跨 Module Interface 迁移没有在同一提交完成。`4c8caef` 中补充了调用方迁移和 `requireObservationValue` 适配，因此链尾恢复通过。

该事实说明：

```text

≠ 跨模块契约已经闭合
```

## 5. `c0aacb8` 的红色回归与提交级证据

本提交不是只根据代码阅读修改，而是先建立能够复现错误语义的红色回归：

1. post-launch Coordinator 在 `handled` 后立即返回，导致“点击后页面未迁移”被错误当作成功；
2. post-launch 已知安装人工阻断被重新命名为 `POST_LAUNCH_DIALOG_MANUAL_ACTION_REQUIRED`，丢失原始安装业务原因；
3. install Coordinator 把稳定 `waiting` 与稳定 `unrecognized` 都映射为 `INSTALL_DIALOG_UNRECOGNIZED`。

修正后的状态语义为：

```text
handled → 继续观察 → none：阶段完成
handled → 相同业务帧持续出现：*_DIALOG_TIMEOUT
稳定 unknown：*_DIALOG_UNRECOGNIZED
已知安装人工阻断：INSTALL_USER_ACTION_REQUIRED
```

新增的 post-launch 8 项测试覆盖：optional-none、handled 后迁移、handled 后不迁移、稳定 unknown、变化状态总超时、取消、真实 OPPO Profile→Controller→Coordinator 多帧回放和安装人工阻断语义。install 组合测试同时证明：同一已识别页面只点击一次，未发生可验证迁移时终局为 `INSTALL_DIALOG_TIMEOUT`。

以后跨 Module 变更必须同时检查：

- 类型/Interface 的生产者和所有调用方；
- 状态所有者、时序和终局 Decision；

- fixture、定向测试和至少一个跨 Seam 测试；

- 提交是否能独立构建、测试、回退，是否依赖 staged/unstaged/untracked 的隐含改动。

测试数量只能作为结果记录，不能作为稳定性结论本身。
