## 1. 一句话定义

用户可以在一个任务中选择 **N 条输入视频** 和 **M 台物理设备**，平台为每个“视频 × 设备”组合生成独立结果，同时复用同一台设备的准备和批处理上下文；不同设备之间并行，同一设备内部保持安全串行，并让每条结果、每次重试和每份证据都能够独立追溯。

核心目标不是简单地“开更多并发”，而是：

1. 先保证结果、日志、检查项和证据的归属准确；
2. 再建立可比较的阶段耗时和资源基线；
3. 只优化平台外围开销，不修改 APK/SDK 内部算法；
4. 在真实设备上证明多设备吞吐和失败收敛；
5. 把同设备多 SDK 实例并行作为后续独立项目。

## 2. 需求背景与要解决的问题

### 2.1 当前业务场景

测试人员需要将同一批视频复制到多台 Android 设备上，使用指定 APK/SDK 执行视频兼容性或处理测试，并查看：

- 每台设备是否执行成功；
- 每条视频在每台设备上的输出是否生成；
- 输入传输、SDK 处理、输出回收和媒体完整性是否通过；
- 设备断线、超时、取消和重试发生在哪里；
- 多设备同时执行时，总耗时和资源占用是否可接受。

### 2.2 现有方案容易产生的错误

| 问题 | 直接后果 |
|---|---|
| 批次公共日志被复制到每条视频 | 报告看起来像每条视频都单独启动了一次批次 |
| 同名检查项使用过宽唯一键 | 不同视频互相覆盖检查结果 |
| 重试覆盖旧 Attempt | 无法解释第一次失败以及最终成功的原因 |
| 用 `1/4`、`2/4` 字符串同时表达顺序和校验 | 前端把处理进度误显示成输入校验结果 |
| 一个视频媒体校验失败导致整批短路 | 其他视频没有结果或被错误标记失败 |
| 用文件名关联输出 | 同名文件覆盖，或输出无法稳定追溯 |
| 只根据架构图宣称并行有效 | 没有真实启动时间、资源和失败率证据 |
| 在同一设备上直接启动多路 SDK | 可能发生目录、缓存、marker、进程和输出互相污染 |

## 3. 范围、边界和非目标

### 3.1 本项目范围

本项目包含：

- 多视频任务创建、固定顺序和输入约束；
- 多设备任务分发和结果矩阵；
- 同设备安全串行、跨设备并行；
- 同一设备上的目录批处理协议适配；
- 视频级输出、检查项、日志、失败和重试证据隔离；
- 设备级和视频级状态聚合；
- 时间线和阶段耗时记录；
- 媒体完整性校验的有界并发实验；
- 2、5、10、15 台设备的阶梯压测；
- 取消、超时、设备断线和一次受控重试的收敛规则；
- 报告 API 和前端展示合同。

### 3.2 明确不包含

以下内容不在本项目内直接实现：

- 同一设备上四条视频同时进入四个 SDK 实例；
- 修改 APK/SDK 内部算法或处理速度；
- 在没有协议保证的情况下绕过输入、输出或媒体完整性校验；
- 用理论计算替代真机压测并承诺“15 台设备必然 5 分钟完成”；
- 用备用设备接管已经创建的 DeviceRun；
- 通过删除失败证据、覆盖 Attempt 或隐藏超时来提高表面成功率。

同设备并发只有在 APK/SDK 明确支持多实例，并且通过单设备 2 路、4 路以及组合场景真机门禁后，才能另立 ADR 和项目实施。

### 3.3 安全并发边界

```text
不同物理设备：允许并行
同一物理设备：一个 Device Lane 内串行
同一设备一次目录批处理：只发送一次 Batch Action
同一设备同时执行的视频数：默认 1
媒体完整性校验：可以独立有界并发，但受 Runner 资源限制
```

## 4. 用户需求

### 4.1 创建任务

用户应能配置：

1. 一个 APK/协议版本；
2. 一条或多条输入视频，默认上限由 `MAX_TASK_VIDEOS` 控制，当前基线为最多 10 条；
3. 设备集合；
4. 连接模式：`auto`、`usb` 或 `network`；
5. 任务超时、设备选择和必要的执行参数。

创建时必须完成：

- 视频数量和单文件大小校验；
- 总输入大小和磁盘预算校验；
- 视频内容 SHA-256 去重；
- TaskVideo 顺序固定；
- 设备可选性和 Endpoint 预校验；
- APK 协议是否支持当前任务模式的校验。

任务创建成功后，视频顺序不可修改；原始文件名只用于展示，不能作为业务主键。

### 4.2 执行任务

系统必须：

- 为每台目标设备创建一个 DeviceRun；
- 为每个“TaskVideo × DeviceRun”创建一个 VideoRunResult；
- 按 TaskVideo.sequence 顺序处理同一设备上的视频；
- 允许不同 DeviceRun 同时进入执行；
- 同一设备的一批视频只执行一次共享的 APK 准备和一次目录批处理 Action（当协议支持目录批处理时）；
- 将每条视频的输入、输出、处理结果和媒体校验结果独立保存。

### 4.3 查看报告

用户应能从任务报告进入以下层级：

```text
Task
 ├─ DeviceRun：设备连接、准备、批次公共事件和设备结论
 └─ TaskVideo
     └─ VideoRunResult：该视频在该设备上的最终结果
         └─ VideoRunAttempt：每次实际物理执行尝试
```

报告必须支持：

- 按设备查看；
- 按视频查看；
- 查看最终结论；
- 展开 Attempt 1、Attempt 2 等历史；
- 查看对应输出文件；
- 查看设备级和视频级检查项；
- 查看设备级和视频级日志；
- 跳转到 Attempt Manifest、设备快照、Logcat、失败证据和输出文件；
- 查看阶段耗时摘要和失败代码。

### 4.4 取消和失败

用户取消任务后：

- 新的视频不得继续开始；
- 正在运行的进程应收到取消信号并尽快停止；
- 已生成的日志、输出和失败证据必须保留；
- 最终任务状态为 `cancelled`，不能被后续自动聚合覆盖。

单条视频失败时：

- 只将对应 VideoRunResult 标记为 `failed`；
- 其他视频继续执行，除非失败属于无法判断后续安全性的设备级基础设施错误；
- 其他视频不能继承该视频的媒体失败、输出失败或 SDK 失败。

设备级基础设施失败且恢复失败时：

- 当前 Attempt 保留为失败；
- 已经执行完成的视频保留各自结果；
- 后续无法执行的视频标记为 `blocked`；
- 不得伪造为 `passed`；
- 不得由备用设备接管原 DeviceRun。

## 5. 业务状态和结果合同

### 5.1 状态定义

| 层级 | 状态 | 含义 |
|---|---|---|
| Task | `queued` | 任务已创建，等待调度 |
| Task | `running` | 至少一个 DeviceRun 正在执行 |
| Task | `passed` | 所有目标 DeviceRun 均通过 |
| Task | `failed` | 存在可明确归因的失败 |
| Task | `cancelled` | 用户取消或任务被取消 |
| DeviceRun / VideoRunResult | `queued` | 尚未开始 |
| DeviceRun / VideoRunResult | `running` | 正在执行 |
| DeviceRun / VideoRunResult | `passed` | 该层级所有必要步骤通过 |
| DeviceRun / VideoRunResult | `failed` | 存在明确失败 |
| DeviceRun / VideoRunResult | `blocked` | 因上游设备级失败无法安全执行或判断 |
| Attempt | `running` | 当前物理尝试进行中 |
| Attempt | `passed` | 本次尝试完成并通过 |
| Attempt | `failed` | 本次尝试失败，历史不可覆盖 |

### 5.2 聚合规则

设备和任务结论必须由事实聚合产生：

```text
存在 failed             → failed
不存在 failed，但有 blocked → blocked
全部目标结果 passed       → passed
仍有 queued/running      → 保持进行中
```

取消状态优先级高于普通成功或失败聚合。聚合不能把已有的终态回退为 `queued` 或 `running`，也不能把 `blocked` 误报为 `passed`。

### 5.3 结果矩阵

```text
Task
├── TaskVideo × N
├── DeviceRun × M
└── VideoRunResult × (N × M)
    └── VideoRunAttempt × 0..K
```

约束：

- `(task_id, sequence)` 唯一；
- `(task_video_id, device_run_id)` 唯一；
- 每个 VideoRunResult 可以有多个 Attempt；
- Attempt 只能追加，不能覆盖历史；
- 主输出必须通过稳定的 `videoRunResultId` 或 `attemptId` 关联；
- 原始文件名不能承担关联、唯一性或目录隔离职责。

## 6. 数据作用域和持久化要求

### 6.1 四层作用域

| 作用域 | 负责表达 | 典型数据 | 写入原则 |
|---|---|---|---|
| Task | 用户请求和总体结论 | 视频数、设备数、任务状态、汇总统计 | 不保存某条视频的执行细节 |
| DeviceRun | 一台设备在一次任务中的共享执行上下文 | Endpoint、租约、设备准备、APK 安装、批次启动/完成、设备级失败 | 公共事件只写一次，不复制到视频 |
| VideoRunResult | 某条视频在某台设备上的最终结果 | 输入、处理、输出、媒体校验、最终状态 | 只写对应视频 |
| VideoRunAttempt | 某条视频的一次物理尝试 | Attempt 状态、连接快照、Manifest、Logcat、失败证据 | 每次重试新建，历史不可覆盖 |

### 6.2 日志和检查项

- 设备级日志使用设备级 Store API；
- 视频级日志使用视频级 Store API；
- 批次公共日志不能通过循环遍历视频来写入；
- 视频级检查项至少以 `videoRunResultId + checkKey` 区分；
- 如果要求完整的重试审计，检查项和日志还应关联 `attemptId`；
- 未完成 Attempt 级迁移前，API 必须明确当前检查项是“最终聚合结果”，原始重试细节从 Evidence 和 Attempt 日志读取；
- 前端列表键必须包含稳定业务 ID，不能只使用 `checkKey` 或原始文件名。

### 6.3 输出和证据目录

建议目录结构：

```text
<dataDir>/tasks/<taskId>/
└── device-runs/<deviceRunId>/
    ├── batch-attempts/<batchAttempt>/
    │   ├── attempt-manifest.json
    │   ├── device-snapshot.json
    │   ├── gate-events.jsonl
    │   └── logcat.log
    └── videos/<taskVideoId>/
        └── attempts/<attemptNumber>/
            ├── input.mp4
            ├── output.mp4
            ├── attempt-manifest.json
            ├── device-snapshot.json
            ├── logcat.log
            └── failure-evidence/
```

要求：

- 每次 Attempt 有稳定且不可复用的目录；
- 同名视频在不同 Task、DeviceRun 或 Attempt 中不能互相覆盖；
- 输出文件与 VideoRunResult/Attempt 可双向追溯；
- 失败证据写入失败路径后，即使报告聚合失败也应尽量保留；
- 历史单视频任务可以继续读取旧路径，但新任务不能依赖旧路径规则。

## 7. 技术方案

### 7.1 模块分工

| 模块 | 职责 | 不应承担的职责 |
|---|---|---|
| TaskService | 校验创建请求、写入 Task/TaskVideo、入队 | 不直接控制 ADB |
| Scheduler / Queue | 生成 DeviceRun 工作、按设备分 lane、调度和取消 | 不决定视频级业务结论 |
| DeviceRegistry | 发现设备、解析物理身份、维护设备可用性 | 不写视频结果 |
| Endpoint Resolver / Connection Controller | 解析和验证 ADB Endpoint，处理网络连接状态和恢复 | 不覆盖旧 Attempt |
| Adb Gateway | 统一执行 ADB 命令、流式 Logcat、超时和进程清理 | 不直接写 SQL |
| Android App Preparer | 安装 APK、处理安装/权限/应用弹窗、设备准备 | 不聚合任务结论 |
| Protocol Executor | 执行单视频或目录批处理协议、识别日志和完成 marker | 不决定跨视频最终聚合 |
| MediaIntegrityChecker | 检查容器、视频流、音频流、解码和元数据 | 不改变 SDK 结果 |
| Database Stores | 持久化 Task、Run、Attempt、Log、Check、Artifact、Evidence 索引 | 不执行外部设备命令 |
| Report API | 聚合并输出稳定的报告合同 | 不重新推断历史事实 |
| Web UI | 按作用域展示状态、证据、时间线和输出 | 不用展示文案替代业务字段 |

数据库访问必须经过 `PlatformDatabase` Facade 和对应 Store；执行器不得直接拼接 SQL。

### 7.2 执行流程

#### A. 创建和排队

```text
用户提交任务
 → 校验 APK、视频、设备、磁盘和 Endpoint
 → 创建 Task + TaskVideo
 → 创建每台设备的 DeviceRun
 → 创建 N×M 个 VideoRunResult
 → 任务入队
```

#### B. 设备级调度

```text
Queue 取出 DeviceRun
 → 获取物理设备 lane / lease
 → 冻结本次执行的 Endpoint 和连接代次
 → 创建批次级 Evidence 上下文
 → 设备准备和 APK 准备
 → 依 TaskVideo.sequence 顺序处理视频
 → 释放 lane / 更新 DeviceRun
```

不同物理设备的 DeviceRun 可以并发；同一物理设备必须互斥。Endpoint 或连接代次失效时，旧执行不得继续写入新 Attempt 的状态。

#### C. 视频级执行

```text
创建 VideoRunAttempt
 → 记录 Attempt Manifest 和设备快照
 → 准备输入并校验远端大小
 → 执行协议或目录批处理
 → 等待明确完成 marker
 → 回收输出并计算 SHA-256
 → 记录输出检查项
 → 执行媒体完整性校验
 → 写入 VideoRunResult 终态
 → 完成 Attempt
```

协议执行器抛出的失败必须带稳定失败码和执行阶段，例如：

```text
INPUT_PUSH_FAILED
SDK_PROCESSING_FAILED
TASK_TIMEOUT
OUTPUT_MISSING
OUTPUT_EMPTY
MEDIA_DECODE_FAILED
MEDIA_INTEGRITY_FAILED
DEVICE_OFFLINE
TASK_CANCELLED
```

### 7.3 目录批处理协议

对于支持目录批处理的 APK/SDK：

1. 一台设备的一批视频只发送一次目录批处理 Action；
2. 输入顺序由 `TaskVideo.sequence` 决定；
3. `Processing file i/n` 只作为进度或日志证据，不能单独作为视频完成事实；
4. 每条输入和输出必须通过稳定的序号、协议返回值或明确文件清单进行映射；
5. 文件系统枚举顺序不稳定时必须失败并报告，不得猜测映射关系；
6. 最后一条视频完成后，才能进入批次输出收敛；
7. 任何一条视频的输出缺失都必须单独记录，不得用其他视频的输出代替；
8. 批次公共阶段写入 DeviceRun，输入/输出/媒体校验写入对应 VideoRunResult。

如果 APK/SDK 只支持单视频协议，则由 Protocol Executor 明确按视频顺序逐条执行，不得伪装成目录批处理。

### 7.4 媒体完整性校验

输出回收完成后，媒体校验应采用以下语义：

```text
收集所有待校验输出
 → 以配置的并发上限执行
 → 每条视频独立捕获异常
 → 等待全部结果结束
 → 逐条写入媒体结果和检查项
 → 最后聚合 DeviceRun 和 Task
```

技术要求：

- 禁止失败即短路的 `Promise.all` 语义；
- 每个视频必须有 `passed`、`failed` 或明确的 `blocked/not_checked`；
- 某条视频校验失败不能吞掉其他视频结果；
- 初始并发上限应配置化，例如 `MAX_CONCURRENT_MEDIA_CHECKS`，默认值必须通过压测确认；
- SHA-256、ffmpeg、ffprobe、ADB pull 共用 Runner 资源时必须设置背压；
- 记录校验耗时、CPU、内存和磁盘占用，以便判断并发是否真的带来收益。

> 如果当前代码尚未具备 `MAX_CONCURRENT_MEDIA_CHECKS`，应把它视为待实现的技术项，而不是现状能力。

### 7.5 时间线和可观测性

至少记录以下 marker：

```text
queued
lease_acquired
device_ready
apk_prepare_started
apk_prepare_finished
input_transfer_started
input_transfer_finished
batch_action_sent
first_processing_log
last_processing_log
marker_detected
output_pull_started
output_pull_finished
media_validation_started
media_validation_finished
finished
```

每个 marker 应满足：

- 有明确写入者和作用域；
- 持久化失败不应破坏核心执行链路；
- 迟到回调不能覆盖已经写入的历史时间；
- 取消后不等待新的业务 marker，但保留已产生的证据和结束状态；
- 缺失 marker 不得伪造，报告应显示缺失并通过日志定位。

阶段耗时摘要建议包括：

```text
queueWaitMs
leaseWaitMs
deviceReadyMs
apkPrepareMs
inputTransferMs
sdkProcessingMs
outputPullMs
mediaValidationMs
totalMs
```

SDK/APK 内部处理时间只能观测，不能直接表述为平台优化收益。

### 7.6 连接、租约和恢复

多设备吞吐建立在设备连接稳定的前提上，因此连接治理属于必要前置技术：

- 物理设备身份不能等同于 ADB transport serial；
- USB、传统网络 ADB、无线 TLS ADB 等 Endpoint 必须独立建模；
- 执行前冻结 Endpoint、连接 generation 和 Attempt 快照；
- Endpoint 失效时，旧执行不得继续写状态；
- 连接恢复必须有 deadline 和稳定失败码；
- 一次受控基础设施重试必须创建新的 Attempt；
- 恢复失败后当前视频失败，后续视频按 `blocked` 规则收敛；
- 网络 ADB 的发现、连接、push、pull 和长命令稳定性必须分别验证，不能用发现成功代表整条链路稳定。

### 7.7 API 和前端合同

推荐报告结构：

```ts
interface ReplicatedReport {
  task: TaskSummary
  deviceRuns: Array<{
    deviceRunId: string
    deviceId: string
    status: RunStatus
    deviceChecks: CheckResult[]
    deviceLogs: ReportLog[]
    timelineDurations?: TimelineDurations
  }>
  videos: Array<{
    taskVideoId: string
    sequence: number
    displayName: string
    deviceResults: Array<{
      videoRunResultId: string
      deviceRunId: string
      status: RunStatus
      checks: CheckResult[]
      logs: ReportLog[]
      outputs: ArtifactView[]
      attempts: AttemptSummary[]
      timelineDurations?: TimelineDurations
    }>
  }>
  summary: {
    inputVideoCount: number
    deviceCount: number
    resultCount: number
    passedCount: number
    failedCount: number
    blockedCount: number
    elapsedMs?: number
  }
}
```

前端规则：

- 播放器绑定 `videoRunResultId` 或输出 Artifact ID，不绑定文件名；
- 页面中的检查项 key 不假设全局唯一；
- 公共设备日志只展示一次；
- 当前视频日志按时间展示；
- Attempt 历史默认折叠，最终结果单独突出；
- 顺序显示为“第 N 条，共 M 条”，校验状态单独显示；
- 缺少输出时展示失败原因和证据链接，不显示伪造播放器或空成功卡片。

## 8. 性能优化项和测量方法

### 8.1 可优化的部分

| 优化项 | 目标 | 约束 |
|---|---|---|
| 媒体校验有界并发 | 减少多视频输出校验的串行等待 | 不得丢结果；受 CPU、内存、磁盘限制 |
| 跨设备并行 | 缩短多设备任务总墙钟时间 | 每设备独占 lane；不能牺牲隔离性 |
| 设备准备复用 | 减少重复 APK 安装、权限和应用准备 | 只在协议和设备状态允许时复用 |
| 输入传输调度 | 降低多个设备同时 push 的等待 | 受 USB/网络和本地磁盘带宽限制 |
| ADB/ffmpeg 背压 | 避免高并发时资源争抢导致尾延迟和失败 | 参数由压测冻结，不凭经验无限放大 |
| 连接预检和恢复 | 减少执行中断和无效重试 | 不得把恢复成功误报为原 Attempt 成功 |

### 8.2 不可直接承诺的部分

- “节省 10～20 秒”只能作为实验目标；
- “单机固定节省约 7 秒”只能作为历史观察值；
- “15 台设备 5 分钟以内”必须由真实阶梯压测产生；
- SDK/APK 内部处理时间不能算作平台已经优化；
- 单次最快结果不代表稳定收益。

### 8.3 基线测试设计

固定以下变量：

- APK 文件和版本；
- 设备型号、Android 版本和连接方式；
- 输入视频集合和顺序；
- 执行超时时间；
- 媒体校验并发上限；
- Runner、磁盘和网络环境。

至少执行：

1. 单设备单视频，连续 10 轮；
2. 单设备四视频目录批次，连续多轮；
3. 两设备四视频，验证启动重叠和结果隔离；
4. 2、5、10、15 台阶梯压测；
5. 受控取消、超时、断线和重试场景。

每轮记录：

- 总耗时、p50、p90、p95；
- 各阶段耗时；
- 设备开始时间差；
- lane 等待时间；
- CPU、内存、磁盘、ffmpeg 进程峰值；
- ADB push/pull 耗时、错误和断线次数；
- 每台设备和每条视频的成功率；
- 输出覆盖、输入污染、报告串联错误数量。

## 9. 分阶段实施路线

### Phase 0：业务语义校正

目标：让报告和持久化数据先“说真话”。

交付：

- Task、DeviceRun、VideoRunResult、Attempt 作用域审计；
- 批次公共日志/检查项改为设备级；
- 视频级输入、输出和媒体校验独立记录；
- Attempt 历史和 Evidence 不覆盖；
- API 和前端使用稳定 ID；
- 旧单视频任务兼容读取。

门禁：四条视频中同名检查项不互相覆盖，公共事件只出现一次，每条视频有独立结果。

### Phase 1：时间线和可比较基线

目标：知道耗时到底发生在排队、准备、传输、SDK、输出还是媒体校验。

交付：

- 完整 marker 契约；
- 真实执行路径写入 marker；
- DeviceRun 和 Attempt 阶段耗时摘要；
- 固定视频集和至少 10 轮基线入口；
- 取消、超时、重试和失败路径的时间线证据。

门禁：时间线缺失可解释，迟到 marker 不覆盖历史，报告可查看分阶段耗时。

### Phase 2：平台外围优化

目标：在不改变 APK/SDK 行为的前提下降低平台等待。

交付：

- 媒体校验有界并发；
- ADB、SHA、ffmpeg 资源背压；
- 跨设备准备和传输调度；
- 全量结果收敛和逐视频落库。

门禁：单视频校验失败不丢其他结果；高并发下失败率、尾延迟和资源峰值不恶化。

### Phase 3：多设备吞吐验证

目标：证明并行带来稳定收益且结果仍可追溯。

顺序：

```text
双设备成功 Gate
 → 5 台
 → 10 台
 → 15 台
```

每一级必须先通过功能和证据门禁，再看性能数据。任何双设备共同超时、共同缺失 marker 或输出链路未完成的情况，都不能进入下一阶梯。

### Phase 4：同设备多实例（独立项目）

启动条件：

- APK/SDK 正式支持多实例或多进程；
- 输入、输出、marker、缓存、临时文件和数据库隔离已证明；
- 设备 CPU、内存、GPU、温度和功耗边界已知；
- 取消、崩溃恢复、重试和 Evidence 隔离已设计；
- 单设备 2 路、4 路真机 Gate 通过。

## 10. 测试与发布门禁

### 10.1 自动化测试

必须覆盖：

- N×M 结果矩阵创建；
- TaskVideo 顺序和去重；
- DeviceRun 与 VideoRunResult 状态聚合；
- 设备级与视频级日志/检查项隔离；
- 同名 checkKey 不覆盖；
- Attempt 1/2 证据不覆盖；
- 有界媒体校验等待全部结果；
- 单视频失败不污染其他视频；
- 取消、超时、断线、恢复和阻塞；
- Endpoint generation 失效时旧执行不能写入；
- API 兼容旧单视频任务；
- 报告输出和 Evidence 路由。

### 10.2 真机测试矩阵

| 场景 | 最低要求 |
|---|---|
| 单视频 × 单设备 | 成功、失败、取消、超时 |
| 四视频 × 单设备 | 只发送一次批处理 Action，四条结果独立 |
| 两视频 × 两设备 | 四条结果和输出正确关联，设备启动时间有重叠 |
| 四视频 × 两设备 | 每台设备一次批处理，输出和日志不串设备 |
| 单视频媒体失败 | 其他视频结果仍可查看 |
| 设备受控断线 | Attempt 1 失败，Attempt 2 独立恢复或明确失败 |
| 批次恢复失败 | 当前视频 failed，后续视频 blocked |
| 运行中取消 | 进程停止，证据保留，任务为 cancelled |
| 历史单视频任务 | 报告仍可读取 |

### 10.3 发布前门禁

- 固定设备和视频集连续至少三轮无跨任务污染；
- 至少两种 Android 设备完成同一批处理门禁；
- 每台设备每个 Batch Attempt 只发送一次 Action；
- 任意输出都可追溯到 `TaskVideo × DeviceRun × Attempt`；
- 失败、重试和取消证据可从报告跳转；
- 双设备成功 Gate 关闭前，不进入 5/10/15 台压测；
- 性能报告包含 p50/p90/p95、失败率和资源峰值；
- 工作区、构建、自动化测试和真机证据身份明确，不能把历史证据冒充当前版本结论。

## 11. 当前实现核对时的重点差异

重新开始实施时，先逐项核对以下内容，不要直接假设历史计划已经全部落地：

1. **结果模型**：确认当前代码和数据库仍以 `TaskVideo → DeviceRun → VideoRunResult → Attempt` 表达，而不是只依赖兼容字段；
2. **批次公共作用域**：确认 `adb.ts` 和协议执行器不会把公共日志、检查项广播到所有视频；
3. **Attempt 关联**：确认检查项、日志和 Evidence 是否都能定位到具体 Attempt；
4. **状态聚合**：确认 `blocked` 不会被设备级聚合错误转换成 `failed` 或 `passed`；
5. **媒体并发**：确认当前配置和实现是否真的存在 `MAX_CONCURRENT_MEDIA_CHECKS`，不存在则列为待实现；
6. **时间线**：确认 marker 是由真实执行阶段写入，而不是只有数据库字段或前端展示；
7. **目录批处理**：确认完成 marker、最后一条视频和输出映射语义在当前 APK 版本上成立；
8. **网络 ADB**：将设备发现、连接、push、pull 和长命令分别验证；
9. **真机证据**：旧分支的 run3/run4 只能作为历史背景，必须重新确认是否与当前代码、APK、设备和输入集一致；
10. **工作区状态**：当前工作区有大量未提交修改，实施、真机 Gate 或回退前不得执行 `reset --hard`、`clean -fd`、覆盖式 checkout 或强推。

## 12. 最终完成定义

只有同时满足以下条件，才能称为“多设备复制执行模式完成”：

1. Task、DeviceRun、VideoRunResult 和 Attempt 的业务边界清晰；
2. 批次公共日志和检查项不再复制到每条视频；
3. 每条视频的输入、输出、媒体完整性和失败证据独立可追溯；
4. 重试会产生新 Attempt，历史不可覆盖；
5. 单条视频失败不会导致其他可判断视频丢失结果；
6. 设备级失败能正确产生 `failed/blocked`，且不会伪造成功；
7. 时间线和阶段耗时可以在报告中查看；
8. 媒体校验并发有界，所有结果都收敛后才聚合；
9. 至少完成双设备成功 Gate，并具备可重复的多设备压测数据；
10. 同一设备仍保持单 lane、单 worker、单批处理 Action；
11. 所有性能结论都有固定环境、分位数、失败率和资源数据；
12. 同设备多 SDK 并行被明确隔离为后续独立项目。

在完成定义满足之前，只能表述为“代码具备部分多设备执行能力”或“已完成某一层验证”，不能表述为“多设备性能优化已经完成”，更不能表述为“同设备四路 SDK 并行已经实现”。
