# 缺陷修复与优化计划（2026-09-08）

> 范围：基于 2026-09-07 ~ 09-08 的两起真实缺陷（多视频任务 logcat/截图下载 404、PJV110 与 Xiaomi 15 Pro 弹窗白名单不识别）及其排查过程，对代码库当前问题做一次系统性收口。
> 性质：执行计划，逐项带验收标准；本文档本身不改动任何运行代码。

## 总原则（每次改动都要过这三条）

1. **已应用到生产库的迁移文件不可删除。** 迁移 runner 的 checksum 门禁和 VACUUM 备份的前提是"迁移历史不可变"。要废弃一张表，新增一个 DROP 迁移，不改旧文件。
2. **一处知识只写一遍。** 文件布局、URL 拼法、领域类型，凡是需要两处以上手抄同步的，都是未来缺陷的藏身处。
3. **每项独立提交，附全量测试结果。** `npx vitest run`（当前基线 412 通过）+ `tsc -p apps/api/tsconfig.json --noEmit` + `tsc -p tsconfig.app.json --noEmit` 双绿才算完成。

### P0-2 恢复 stash@{0} 的网络 ADB 自愈工作并推送远端

- 现状：68 个文件（+15430/-2310）只存在于 `stash@{0}`，stash 不随远端备份，一次误 drop 即永久丢失。分支 `feat/network-adb-self-healing-v1` 已存在且与 main 同点。
- 做法（在 P0-1 提交完之后执行，避免 stash apply 与工作区互相污染）：
  1. `git checkout feat/network-adb-self-healing-v1`
  2. `git stash apply stash@{0}`（不要用 pop，冲突时 stash 仍在）
  3. 解决与 main 新提交（P0-1 的 A/B）的冲突——重点：`task-store.ts`、`evidence-routes.ts`、`types.ts`、`stores.test.ts` 双方都改过

- 验收：远端分支更新；本地 `git stash list` 该条目可安全保留或清除；412+ 用例全绿。
- 风险：中。冲突解决需要人工判断两边语义；建议解决冲突时逐文件对照本文档"总原则 2"。

### P0-3 修复被删除的迁移 010/011（重建能力缺口）

- 现状：生产库 `schema_migrations` 已应用 `010-execution-timeline`、`011-task-idempotency`（共 11 条），但代码迁移目录只剩 001-009。全新环境重建数据库会少 `task_idempotency` 等表，schema 漂移已发生。
- 有利条件：两个文件在 git 历史 `d145bf5`（"temporary current-version gate snapshot"，2026-08-19）中完整存在。

  3. 启动验证：live DB 上两迁移已在 `schema_migrations` 中，runner 按 id 跳过、不重放；fresh DB（测试内存库）会正常创建全部表

## P1 缺陷修复与结构优化（P0 完成后 2 周内）

### P1-1 Evidence 布局单一事实来源（消灭 logcat-404 这类缺陷的土壤）

- 问题：attempt 目录布局知识分散三处——`adb.ts:218 localAttemptDirectory`（写）、`evidence-routes.ts resolveRunScopedFile`（读，硬编码候选）、`task-store.ts`（拼 URL）。布局再变一次，还会再出一次今天的 404。
- 做法：新建 `execution/attempt-evidence-layout.ts`，唯一导出：
  - `attemptDirectory(input: { tasksDir, taskId, runId, taskVideoId?, attemptNumber })`（封装"单视频首 attempt 用 run 根、多视频/重试用 videos/<tv>/attempts/<n>"规则）
  - `runScopedEvidenceCandidates(...)`、`logcatRelativePath`、`finalScreenshotRelativePath`、`evidenceDownloadUrl(...)`
  - 三个使用方全部改为引用该模块。
- 验收：新增布局单测（三种布局 × 存在性组合）；现有 evidence-routes / adb / stores 测试不动断言全绿。
- 预估：半天。

### P1-2 `TaskStore.list()` N+1（task-store.ts:109）

- 问题：列表页每个任务完整执行一次 `get()`（videos × devices 的 checks/logs/outputs/attempt 多轮查询）。任务积到几十个后列表线性变慢。
- 做法：列表走专用摘要 SQL（task + run 状态聚合一次取出），只回列表页实际渲染的字段；`get()` 保留给详情。
- 验收：现有路由测试绿；新增"列表查询次数不随任务数增长"的断言（可 mock db 计数）。
- 预估：半天。

### P1-3 报告日志/检查项无上限直出

- 问题：`run.logs`、`run.checks`、视频级同名集合全量塞进任务详情和报告响应；长任务（120s 超时 × logcat 轮询写入）响应体膨胀。
- 做法：视图层截断 + `?logsLimit=` 参数；详情页"查看全部"走分页接口（复用 evidence 分页思路）。
- 验收：报告响应体积有上限断言；前端展示不受影响。
- 预估：1 天（含前端）。

### P1-4 evidence 路由错误语义（吞错）

- 问题：`catch {}` 把 ENOENT（真没收集）和 EACCES/EMFILE（IO 故障）都压成 404，排障时无法区分（今天排查时实际受害）。
- 做法：`access/stat` 的 catch 里判断 `error.code`：ENOENT → 404 原语义；其他 → `request.log.error` + 500 `EVIDENCE_IO_ERROR`。
- 验收：单测构造两种错误分别断言 404/500。
- 预估：2 小时。

### P1-5 领域类型双份手抄收敛（第一步）

- 问题：`web/src/types/index.ts`（461 行）与 `apps/api/src/types.ts`（361 行）人工同步；本次加两个字段改了四处。
- 做法（渐进，不一次到位）：
  1. 第一步（本次计划内）：新增 `shared/dto.ts` 存放纯 DTO（`VideoRunResultView`、`DeviceRunView`、`TaskVideoView`、`CheckResult`、`MediaMetadata` 等），api 与 web 的 tsconfig 都指向它，各自 re-export；
  2. 第二步（二期前）：评估 zod schema 单一定义 + 推导类型，顺带解决入参校验。
- 验收：删除两份文件中已迁移的重复定义后双工程 tsc 绿；web 构建产物体积无明显变化。
- 预估：1 天。

### P1-6 httpClient URL 白名单机制显式化

- 问题：前端靠 key 名字面量（`previewUrl|downloadUrl|logcatUrl|screenshotUrl`）匹配补 origin（httpClient.ts:203），漏一个 key 就静默错链。
- 做法：与 P1-1 的 `evidenceDownloadUrl` 联动——DTO 中 URL 字段统一 `XxxUrl` 后缀 + 一个 `KnownUrlKeys` 常量数组从 shared 导出，httpClient 引用它；或改为后端在开发模式直接下发绝对 URL（`config.publicBaseUrl`）。
- 验收：新增一个 URL 字段的"忘记注册"场景测试（用类型层面的 `Record<KnownUrlKeys,…>` 约束或运行时遍历断言）。
- 预估：半天。

### P1-7 依赖清理

- 移除 `zustand`（根 package.json 声明、全库 0 引用）。`pnpm remove zustand` + lockfile 更新。
- 预估：15 分钟。
