# SDK 云测试平台：重新规划与阶段评审

> 评审日期：2026-08-07（Asia/Shanghai）
> 评审对象：正式仓库 `main`、隔离稳定化 worktree `codex/stabilization-snapshot`、现有代码、测试、文档和历史运行记录。
> 本文是执行规划，不把历史猜测写成事实；每个结论标注为“已确认事实”“高概率判断”“待验证假设”或“建议决策”。

## 1. 这次评审真正要解决的问题

用户的目标不是减少文件数量，而是同时获得：

- 当前 Android 流程的可解释稳定性；
- 新增机型时局部扩展，不牵动其他机型；
- 后续代码易维护、可回退、可验证；
- 高内聚、低耦合，但不把业务复杂度泄漏到主流程；
- 一次变更能够把相关接口、状态、时序、错误、Evidence 和测试一起对齐。

因此，本项目后续的成功标准不再是“增加了多少 Module”或“单测通过多少项”，而是：

> 一个 Device Run 能绑定明确的代码版本、协议版本、Profile、输入、设备快照、观察证据、决策路径、输出和失败语义；新增机型默认不修改主业务编排。

## 2. 结论口径

### 2.1 已确认事实

1. 正式 `main` 仍是混合工作树，HEAD、index 和完整 working tree 不是同一版本；正式仓库不能直接作为本轮稳定化发布基线。
2. 隔离 worktree 从 `3f70307d74864c3517117f6220deab6d6acda829` 现场 checkpoint 已重建五个代码提交：`19c73ad`、`794d9cf`、`4c8caef`、`c539018`、`71348d9`；代码改动已不再依赖 untracked 源码，当前仅治理文档待提交；其中 `794d9cf` 的 API TypeScript 未通过，因此不能作为独立自动化基线。
3. 隔离 worktree 链尾 `71348d9` 的自动化验证已通过：45 个测试文件、281 项测试；TypeScript 检查、Web/API 构建、Android `assembleDebug` 和 `git diff --check` 通过。逐提交复核发现 `794d9cf` 的 API TypeScript 未通过，详见《稳定化逐提交门禁记录-2026-08-07》。
4. 当前没有 Android 真机连接，因此没有 V2324A、荣耀 X50、PJV110 或对照机的本轮真机通过证据。
5. `AdbRunExecutor` 仍直接编排连接、应用准备、输入传输、Logcat、Morpho 启动、完成判断、输出回收、媒体校验、状态落库和清理；文件当前约 873 行。
6. `AdbRunExecutor` 仍直接持有多个 Morpho 生命周期状态，包括输出路径、协议失败、业务启动、启动证据接收、业务日志启动和 Logcat 失败。
7. Profile / Controller / Coordinator 已有 `waiting` 止血逻辑和第一版共享 `InstallProgressSignature`；但包状态、权限状态、动作结果、VerifyTransition、终局 Decision 和动作状态的唯一所有者尚未完成。
8. ADB 直接授权成功但仍残留权限控制器窗口的分支，已在隔离 worktree 改为复用 `RuntimePermissionDialogCoordinator` 的阶段级处理，并增加 residual runtime-permission 的 6 项状态测试；该分支仍缺少真实多帧回放和真机证据。
9. 已增加共享 `InstallProgressSignature`，使 Controller 与三个阶段 Coordinator 至少使用同一套“业务观察状态是否变化”的比较语义；当前仍未把包状态、权限状态和终局 Decision 完整纳入该模型。
10. 含义模糊且可缺省的 `activeInstall?: boolean` 已替换为必填 `DialogBusinessPhase`（`install` / `runtime-permission` / `post-launch`）。动作 Profile 按 `allowedPhases` 限制；已知 block 分类不再因业务阶段改变而退化成 unknown；PostLaunch 预检查会同时识别动作 Profile 和 block-only Profile。
11. `TaskExecutionError` 当前只有 `message` 和自由字符串 `code`，尚未包含类别、阶段、可重试性、置信度和 Evidence 引用。
12. 任务取消目前把 queued/running 的 Device Run 标记为 `blocked`，这是否符合产品语义尚未通过明确需求确认；暂不能直接判定为 bug。

### 2.2 高概率判断

1. Morpho 旧启动探测的输出截断/严格解析误判，与历史 V2324A 的 `SDK_START_FAILED` 现象高度吻合；但没有当次完整原始 Evidence，不能断言这是唯一根因。
2. 当前故障的主要放大因素是跨 Module 契约未同步演进：Profile、Controller、Coordinator、主流程对 waiting、观察失败、业务失败和成功证据的解释不完全一致。
3. 模块过多不是直接根因；更准确地说，技术动作拆得较细，但完整业务规则没有被少数深业务 Module 吸收，复杂度通过共享状态、调用顺序和错误优先级泄漏到主流程。
4. 混合工作树不是每次运行故障的直接根因，但会显著放大归因、验证、回退和机型回归风险，并可能让不同临时兼容逻辑同时生效。

### 2.3 待验证假设

1. 修复后的 Morpho 探测是否能在 V2324A 和至少一台对照机上稳定区分“观察不完整”和“业务确实未启动”。
2. `waiting` 与有效进展签名能否在荣耀 X50、PJV110 及普通 Android fixture/真机上避免重复点击误判，同时不放过真正 stalled 页面。
3. 新增 Profile 是否会改变已有 Profile 的匹配优先级、通用 fallback 或旧机型行为。
4. Device Run 取消后的 `blocked` 是否是既定业务语义，还是数据库状态契约遗漏。
5. 当前历史通过/失败比例不能作为新代码稳定率，除非每次运行都能关联 commit、dirty 状态、Protocol/Profile 版本和设备快照。

## 3. 重新规划后的目标架构

### 3.1 对外只保留少数业务深 Module

目标不是删除内部小模块，而是把它们收回业务深 Module 内部：

```text
TaskOrchestrator
  ├── DeviceSession
  ├── AndroidAppPreparer
  ├── ProtocolExecutor
  │     ├── CarrierProtocolExecutor
  │     └── MorphoProtocolExecutor
  ├── ArtifactCollector
  └── AttemptEvidenceRecorder
```

主流程只负责业务阶段和结果汇总：

```text
validate → prepare → transfer → execute → collect → conclude → cleanup
```

主流程不应了解：

- Morpho 的每个 Probe section；
- Logcat 监听的内部生命周期；
- OEM Profile 的节点和点击坐标；
- 某个观察命令的退出码如何解释；
- 某个协议内部 boolean 的组合。

### 3.2 Observation、Classification、Decision、Action 分层

```text
Raw Observation
    ↓
Profile / Classifier
    ↓
Business State Machine（唯一 Decision 所有者）
    ↓
Controller / Adapter（执行动作）
    ↓
Verify Transition
    ↓
Final State
```

必须遵守：

- 观察失败不能自动降级成普通缺失；
- 一次观察不直接决定最终业务失败；
- fingerprint 相同不等于 stalled；
- 点击后必须允许 waiting 状态；
- timeout、retry、cancel 和 cleanup 的所有者必须明确；
- 成功证据与诊断告警要有明确优先级，不能被无关观察错误覆盖。

### 3.3 模块深度的判断标准

后续不用“模块小”判断设计好坏，而用以下问题判断：

1. 一个业务规则变化时，是否主要只修改一个业务 Module；
2. 调用者是否需要知道内部调用顺序和多个 timeout；
3. 是否存在同一状态的多个 writer；
4. 是否需要跨越公开 Interface 才能测试完整行为；
5. 新机型适配是否必须修改主流程；
6. 删除该 Module 后，复杂度是否重新散落到多个调用点。

## 4. 稳定化阶段、交付物和退出条件

### S0：冻结版本与恢复可追溯性

**目标**：不再让混合工作树成为未知变量。

**交付物**：

- 正式 `main` 的只读现场记录；
- 稳定化 worktree checkpoint；
- 逻辑变更切片清单；
- 每次运行的版本身份模板；
- 受影响机型矩阵；
- 现有 Evidence 和 fixture 索引。

**退出条件**：

- 没有执行破坏性清理；
- 稳定化切片能在隔离 worktree 独立测试/构建；
- 每个切片明确依赖和回退边界；
- 真机记录至少包含 commit SHA、dirty flag、Protocol/Profile 版本。

**当前判断**：自动化侧基本完成。现场已隔离并形成四个业务提交；仍需 detached worktree 独立全量门禁记录和真机运行身份记录。

### S1：Morpho 启动链止血

**目标**：把“观察不完整”与“业务启动失败”分开。

**当前已有**：

- 分段 Probe：services、process、power、windowPolicy；
- stdout/stderr 完整 Evidence、字节数和截断标记；
- Probe Observation 与启动 Decision 分离；
- 启动探测不完整时允许后续业务 Logcat 证据继续竞争；
- ADB 观察三态：present、absent、failed；
- `result.json` 基础结构解析已开始收敛。

**还必须完成**：

- 载体 `result.json` 空文件、损坏、字段非法和 taskId 不匹配的组合测试；
- 业务失败日志、Probe 失败、Logcat 启动失败同时出现时的优先级测试；
- Logcat 失败后的取消、force-stop 和清理测试；
- V2324A 与对照机真机回放；
- 将 Morpho 决策证据保存为可查询的结构化记录，而不只写日志。

**退出条件**：

- 不完整 Probe 不再直接产生 `SDK_START_FAILED`；
- 有明确的启动成功证据优先级；
- 失败报告能够指向原始 Probe、Logcat 和决策摘要；
- 目标机与对照机重复运行结果可追溯。

### S2：OEM 安装状态机闭环

**目标**：让 Profile、Controller 和 Coordinator 使用同一个业务状态模型。

**目标状态**：

```text
completed
action-required
waiting
unknown
stalled
manual-action-required
unsafe
failed
```

**必须完成**：

- 引入 `InstallProgressSignature`，不能只用 fingerprint；
- 将点击历史和动作计数从 Controller 逐步迁移到 Coordinator/State Machine；
- Profile 只分类事实和提供安全动作候选；
- Controller 只执行动作并返回结果；
- Coordinator 唯一决定 waiting、stalled、timeout 和终局错误；
- 目标机、同厂商机型、跨厂商对照机 fixture 回放。

**退出条件**：

- 重复页面只进入 waiting，不直接失败；
- 业务字段发生变化会重置停滞计时；
- 真正无进展达到规则阈值才进入 stalled/unknown；
- 任何未知或不安全页面不发生盲点；
- 新 Profile 不改变无关旧 Profile 的匹配结果。

### S3：Morpho Protocol Seam 收敛

**目标**：让 Morpho 生命周期由 `MorphoProtocolExecutor` 唯一拥有。

**迁移顺序**：

1. 先定义内部 `MorphoExecutionContext` 和 `MorphoExecutionResult`；
2. 把启动 Probe、Logcat 解析、完成判断、输出路径发现和清理迁移到该实现；
3. 先由 `AdbRunExecutor` 适配旧结果，不同步改变数据库状态语义；
4. 用跨 Seam 测试替换主流程 boolean 组合测试；
5. 删除主流程中 Morpho 专属状态和分支。

**退出条件**：

- `AdbRunExecutor` 不再持有 Morpho 专属 boolean；
- ProtocolExecutor 对外接口不暴露 Probe 内部细节；
- Carrier 和 Morpho 两类协议均有独立执行实现；
- 取消、超时、清理路径均由执行模块覆盖。

### S4：统一 Failure、Evidence 和回放

**目标**：失败可解释、可检索、可重放。

**建议结构**：

```ts
interface ExecutionFailure {
  code: string
  category: 'observation' | 'device' | 'business' | 'protocol' | 'infrastructure' | 'user_action' | 'cancelled'
  phase: DeviceRunPhase
  retryability: 'never' | 'safe' | 'conditional'
  confidence: 'confirmed' | 'probable' | 'unknown'
  message: string
  evidenceRefs: string[]
  cause?: unknown
}
```

**注意**：先建立 Registry 和映射测试，再逐步迁移，不要一次性改所有 API、数据库和前端。

**退出条件**：

- 新错误必须注册；
- 观察、业务、设备和用户操作错误能区分；
- Evidence 与失败决策有关联；
- 历史关键故障至少有一个 fixture 可回放；
- UI/API 能展示稳定 code 和人类可读解释。

### S5：扩展治理

**目标**：新增机型成为局部适配，而不是主流程修改。

**每个 Profile/Adapter 必须交付**：

- 输入 fixture；
- 预期分类；
- 允许动作和禁止动作；
- waiting/transition/stalled 行为；
- 同厂商回归；
- 跨厂商对照；
- 独立逻辑提交；
- 运行身份和回退说明。

**退出条件**：

- 新机型默认不修改 TaskOrchestrator；
- 旧 Profile 回放不变；
- 变更通过跨模块契约清单；
- clean/dirty 版本 Gate 生效；
- 失败可以定位到 Profile、协议、观察或设备层。

## 6. 机型回归 Gate

没有真机时先做 fixture 回放；有真机后每个切片至少执行：

| 组别 | 设备范围 | 目的 |
|---|---|---|
| 目标机 | 本次受影响机型 | 证明目标故障是否改善 |
| 同厂商 | 已有相同厂商机型 | 防止厂商规则误伤同类设备 |
| 跨厂商对照 | Xiaomi、vivo、OPPO、Huawei/普通 Android 中可用设备 | 防止通用逻辑扩散 |
| 旧稳定样本 | 最近已知通过样本 | 防止回归历史成功路径 |

每台设备每个关键切片至少记录：

```text
commit SHA
working tree dirty flag
Protocol ID/version
Profile IDs/version
device snapshot
connection kind
attempt number
result
failure
Evidence directory
```

**重要边界**：自动化测试通过只证明代码路径在测试输入上通过；真机 Gate 未完成前，不得称为机型稳定。

## 7.1 本轮已实际落地的跨模块修正

在隔离稳定化 worktree 中，本轮不只补了单个 Controller，而是沿完整权限阶段契约做了一个垂直切片：

```text
DefaultAndroidAppPreparer
→ RuntimePermissionDialogCoordinator
→ SystemDialogController
→ DialogInteractionState / DialogProgressTracker
→ 统一的 residual dialog 结果
```

已确认的代码行为：

- ADB 授权成功后若仍观察到权限控制器窗口，不再由 `DefaultAndroidAppPreparer` 单次调用并只处理 `handled`；
- `none` 表示残留窗口消失，可以继续；
- `handled` 表示严格白名单动作完成，随后重新验证权限；
- `unrecognized`/`waiting` 进入阶段级 grace/timeout，而不是被当成“没有问题”或立即终局失败；
- 未知残留页面最终映射为权限阶段错误，并保存超时诊断；
- 已增加跨 `DefaultAndroidAppPreparer` 的回归测试，证明未知残留权限页面不会被误当成可忽略的启动后提示。

这只是一个契约对齐样例，不代表 OEM 完整状态机已经完成。

### 6.1 本轮新增的阶段契约对齐样例

已确认完成：

- `activeInstall?: boolean` 被必填 `DialogBusinessPhase` 取代，调用方必须声明 `install`、`runtime-permission` 或 `post-launch`；
- 动作 Profile 通过 `allowedPhases` 限制动作可执行阶段，安装动作不会在 post-launch 阶段被复用；
- block-only Profile 保持页面风险分类，不因当前阶段不允许点击而退化成 `unrecognized`；
- `PostLaunchDialogCoordinator` 的预检查同时考虑动作 Profile 和 block-only Profile；
- 已增加跨 `DefaultAndroidAppPreparer` 的回归测试，明确人工阻断页面必须返回 `POST_LAUNCH_DIALOG_MANUAL_ACTION_REQUIRED`，不能静默继续。

这一修改解决的是一条已经复现的跨 Module 契约错位，不等于所有 OEM 页面、权限残留和机型组合都已完成验证。

- 新增非必要 OEM Profile；

- 通过全局扩大 timeout 处理误判；
- 通用 OCR、固定坐标或盲点；
- iOS/HarmonyOS 和微服务化扩展；
- 无第二个真实 Adapter 的过度抽象。

## 8. 当前不能宣称

- 当前 `main` 是发布基线；
- 281 项自动化测试等于真机稳定；
- V2324A 已确认是输出截断唯一根因；
- PJV110/荣耀问题已被单个 Profile 彻底解决；
- 新增机型不会影响旧机型；
- 历史运行统计可直接代表当前版本稳定率。

## 9. 当前首要决策

当前项目不需要继续扩大功能范围，而需要进入“稳定化和契约收敛期”：

```text
冻结混合现场
→ 业务切片化提交
→ 先修观察/决策契约
→ 用 fixture 和真机 Gate 证明
→ 再收敛深 Module
→ 最后恢复机型扩展
```

这条路线保留模块化、扩展性和维护性，但把复杂度收回少数业务深 Module，而不是继续把技术动作暴露给主流程。
